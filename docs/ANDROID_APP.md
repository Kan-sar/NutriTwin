# NutriTwin Android

The Android client reuses the Flutter/API workflows. The phone layout follows
Cronometer's public mobile reference: Discover tabs, cream background, white cards,
orange add action, bottom navigation, and dated meal groups. It retains NutriTwin
branding and calculations. It is a reference-based adaptation, not a pixel-verified
replica of every Cronometer screen. Unimplemented tracking features are not shown.

## Install and connect

Install `releases/android/NutriTwin-0.3.0.apk` on Android 7.0 or newer. The universal
APK supports ARM, ARM64 and x86_64. It is a release-mode academic sideload build,
signed with a development certificate; it is not a Play Store production release.

On sign-in, tap **Server connection**. Enter the origin of your NutriTwin API:

- Android emulator: `http://10.0.2.2:8000` (the packaged default).
- Physical phone: your computer's Wi-Fi address, such as `http://192.168.1.10:8000`.
- Hosted backend: its HTTPS origin.

For a physical phone, start the API listening on `0.0.0.0`, connect both devices
to the same trusted Wi-Fi, and allow the API port through the private-network
firewall. The API and database must be running; the APK does not contain a server
or food database. Use the existing local run guide to start the NutriTwin backend.
The current local backend includes the recipe/composition endpoints used by Foods
and Report; older server revisions may lack those endpoints.

Server selection lasts for the app session. Tokens remain in memory and sign-out
clears credentials. HTTP is enabled for local development; use HTTPS for real
accounts over remote networks. App backups are disabled. No credentials or user
records are bundled. Offline synchronization and persistent settings remain open.

## Build

Use pinned Flutter 3.47.2 / Dart 3.13.2, JDK 17+, Android SDK platform 36,
and NDK 28.2.13676358 (the Flutter template default). From `apps/mobile`:

```text
flutter pub get --enforce-lockfile
flutter analyze
flutter test
flutter build apk --release --dart-define=API_BASE_URL=http://10.0.2.2:8000
```

The Android workflow repeats client checks and publishes a downloadable APK with
SHA-256. Development signing keys are generated by the build environment and are
not committed. Different build environments can produce different certificates;
an upgrade signed with a different key requires uninstalling the previous build.
A persistent protected release key is required before production distribution.
